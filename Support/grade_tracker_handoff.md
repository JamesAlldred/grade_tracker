## This session: storage mode detection fixed - was reporting "Claude storage" (and possibly not saving) on locally-downloaded copies
Reported symptom: a copy downloaded via "Set default data" and opened locally showed "saving to Claude storage" instead of local storage, and changes may not have actually been saved. Root cause: `USE_CLAUDE_STORAGE` was decided purely by `typeof window.storage !== 'undefined'` - true even outside a genuine Claude artifact, because a browser environment (a Claude browser extension was the suspect, given the bookmarks bar visible in the screenshot) can inject a `window.storage`-shaped object into every page it touches, not just claude.ai artifacts. It existed, had `.get`/`.set`, looked exactly like the real thing, but didn't actually persist anything - so the app confidently reported the wrong storage location and saves could silently vanish.

Fixed in both files with the same edits: `USE_CLAUDE_STORAGE`/`STORAGE_MODE_LABEL` (`const`s, decided once at parse time from existence alone) replaced by `USE_CLAUDE_STORAGE`/`storageModeLabel` (mutable `let`s, both starting pessimistic - assume plain `localStorage` - and only flipped to Claude storage after `detectStorageMode()` actually proves it works). That function does a same-session set-then-get round trip on a disposable probe key (`` `${STORAGE_KEY}-probe` ``, deleted again immediately after) before trusting `window.storage` for anything real; only a value that reads back byte-for-byte as written counts as genuinely working. `storageSave`/`storageLoad` also now catch a failure that happens later, mid-session (the bridge working at startup but dying afterwards), downgrading to `localStorage` for that operation and every one after it rather than losing the save, and `saveData()` now shows a toast when that downgrade happens so it's not silent. The startup sequence changed from a synchronous label assignment to `detectStorageMode().then(() => { updateStorageModeLabel(); loadTheme(); ...})` - negligible added delay in the common (no `window.storage` at all) case, since the round trip is skipped entirely when nothing that looks like `window.storage` is even present.

**Verified with the jsdom harness, on both files separately, injecting different `window.storage` mocks via jsdom's `beforeParse` (needed since the detection runs at the very top of page load, before any test code can otherwise intervene)**: (A) no `window.storage` at all → correctly stays on `localStorage`, save genuinely lands there; (B) a properly-working mock (real in-memory get/set/delete) → correctly detected and used, save genuinely lands there; (C) **the actual reported bug** - a mock that has working-looking `get`/`set` functions but silently never persists anything (`set` no-ops, `get` always returns null) → correctly fails the probe, falls back to `localStorage`, and the real save still lands there rather than vanishing; (D) a mock that throws outright during the probe → handled gracefully, no uncaught error, still saves via `localStorage`; (E) a mock that passes the initial probe but then throws on a later real `saveData()` call → downgrades mid-session, the save still lands in `localStorage` instead of being lost, a toast explains what happened, and the on-page label updates to match. ## Previous session: "Set default data" button, next to Save
A button next to Save that bakes the file's current data into `DEFAULT_DATA` and re-downloads the whole file, so a completely fresh load (new device, cleared browser, no saved storage at all) starts from today's real data rather than whatever was last baked in by hand. Confirmed via a custom Yes/No popup, not `window.confirm()` - same reasoning as everywhere else this file avoids native dialogs (see the `removeYear` comment): unreliable inside the embedded preview.

**Why a download, not an in-place save**: a page genuinely cannot overwrite the file it was opened from - no server, no filesystem write access, by design of the web platform. So "set default data" can only mean "download an updated copy of this file, which you then save over your existing one." The confirm modal's own wording says this explicitly, and so does the toast afterwards - deliberately not implying anything more automatic than that.

**How it works**: `OWN_SOURCE_HTML` is captured as literally the first statement this script runs (even before `DEFAULT_DATA` itself, positionally - doesn't matter, since capturing `outerHTML` only cares about what the browser's HTML parser has already built, not execution order, and by the time ANY script code runs the entire document - including that same script tag's own full text - is already fully parsed into the DOM). This guarantees the snapshot is the file exactly as authored, before `render()` has touched a single placeholder div, so the download can never accidentally bake in some rendered chart or other live-DOM artefact. `locateDefaultDataBlock` finds the existing `const DEFAULT_DATA = { ... };` inside that snapshot by searching for the literal start marker and the first `\n};` after it - relying on the closing brace always sitting alone on its own line at zero indentation, the same convention this block has been hand-written in every time it's been rebaked by hand in past sessions, and the only convention `buildDefaultDataBlock` itself ever produces (so repeat uses of the button stay self-consistent even though the very first search still depends on what's already there). `buildDefaultDataBlock` is just `JSON.stringify(state, null, 2)` with its outer `{`/`}` stripped and `const DEFAULT_DATA = {`/`};` wrapped back around it, plus a dated comment - the person doesn't need to come back and ask for a manual rebake any more, this is that same manual process, self-served.

**Verified with the jsdom harness**: `OWN_SOURCE_HTML` is a complete, well-formed document containing the real `DEFAULT_DATA` block, captured separately from (and not reflecting) the live, already-rendered DOM at the point the check runs; `locateDefaultDataBlock` returns bounds that genuinely bracket `const DEFAULT_DATA = { ... };`; `buildDefaultDataBlock`'s output is syntactically valid JS whose parsed object is deep-equal to the live `state` at the moment it's called; a full click-through (edit a module's name to a unique marker, call the real button handler, answer the modal's Yes button via an actual dispatched click rather than calling the resolver directly, capture what's handed to `URL.createObjectURL`) produces a `grade_tracker.html` download whose text contains that marker; most importantly, **that downloaded HTML was itself loaded fresh in a second jsdom instance with no storage, and its own `state.modules[0].name` came back as the marker** - i.e. the rebake doesn't just insert a string that looks right, a fresh load of the result genuinely defaults to the new data, and its `calcSummary()` still computes correctly too. ## Working style / preservation constraints
- Prefers **scoped, iterative changes** — build on top of the existing file, don't regenerate from scratch.
- Always state assumptions briefly and preserve existing working functionality unless a change is explicitly requested.
- No em dashes, no tricolons, no `--` for parentheses (use `()` or commas) — this is a stated formatting preference for prose, not code.
- Points out errors/bugs directly rather than working around them silently.
- When adding a new free-text field, confirm the intended default value explicitly rather than assuming it should match an unrelated existing field's convention. The module feedback box defaults to `''`; the Course/Part-level Steps field defaults to `'-'` by explicit instruction, a genuinely different, deliberate choice, not an inconsistency to "fix" later. Type (also Part-level) went further still — it changed shape entirely partway through this project's life, from free text defaulting `'-'` to a fixed dropdown defaulting `''`, a reminder that even an established default for a specific field isn't necessarily permanent if the field's own nature changes.
- Every non-trivial or calculation-touching change is verified with a Node.js + jsdom test harness before being handed over — this has been the consistent pattern across every session and has caught several real bugs (see "Bugs found and fixed" sections below). Load the actual HTML file, run its script in a simulated DOM, call functions directly. Top-level `let`/`const` globals (like `state`) are **not** accessible as `window.state` from outside the page's own script context — use `win.eval('...')` to read/write them from a test harness, not `win.state = ...`. Top-level `function` declarations *are* accessible directly as `window.functionName` (or `win.functionName` from Node) — useful when a test needs to pass real object references (e.g. DOM nodes) that can't survive being serialized into an `eval` string, see "Testing approach" below.
- The app has a genuine `setInterval` running (the save-status refresh). Any jsdom test script needs an explicit `process.exit(0)` after its assertions, or the live timer keeps Node's event loop open and the script hangs.
- When something doesn't work as expected, don't assume it's a code bug — trace it, reproduce it directly, and confirm the actual root cause before touching code. Several "bugs" across sessions turned out to be the *test's* own setup mistake, not the app.
- When investigating a report that doesn't reproduce, say so plainly and ask what specifically is still wrong, rather than re-guessing.

## Architecture

**Storage (dual-mode):**
- `window.storage.get/set` — used automatically when running inside a Claude artifact (persists via Claude's storage).
- Falls back to `localStorage` when `window.storage` is unavailable (e.g. a downloaded standalone HTML file opened in a browser).
- Data entered while using the tracker inside Claude does NOT carry over to a downloaded standalone copy. Export/Import is the deliberate workaround.
- Theme preference, "Advanced" column-visibility, "Assignments" panel-visibility, and the one-time empty-data-reminder flag are stored under **separate keys** from the main academic data (`grade-tracker-v1`) — device/display preferences and view-state, not data, intentionally excluded from export/import.
- **Import always saves immediately via `saveData()`, never via the debounced `scheduleSave()`.** A one-off action like import should never risk losing the save to a 1-second debounce timer.
- **Local-file storage is tied to the exact file path.** Moving the `.html` file to a new folder or opening it on a different device makes localStorage start completely empty at that new location. The safe procedure: **Export data → move the file → Import data** at the new location.

**Side courses terminology, fixed since it was first established — use these terms consistently, not looser phrasing like "provider level" or "components":**
- **Folder** — the provider grouping (e.g. "freeCodeCamp"). `state.sideCourseFolders`.
- **Course** — one individual course (e.g. "Python Certification"). `state.sideCourses`.
- **Part** — one component/step inside a course (e.g. "Python Basics"). `course.components`. Displayed in the UI as "N parts", not "N components", though the underlying field name (`components`) is unchanged.

**Undo:** `pushHistory()` snapshots the *entire* `state` object before any mutating action; `undo()` restores that snapshot wholesale. This makes most structural features "free" to make undo-safe — as long as a new mutating function only touches things living inside `state` and calls `pushHistory()` once before mutating, undo just works. What-if overrides, `expandedComponentModules`, `expandedSideCourses`, `expandedFolders`, `semRadarView`/`semBenchmarkView`, drag session state (both `dragState` and `courseDragState`), and view-state generally are NOT part of undo history, by design — deliberately not saved either, so they always start fresh (Overall/collapsed) on reload, same as they always have.

## Horizontal scroll position preserved across render() (prior session)

## Side course folders (prior session — the largest single change from that session, read in full before touching course drag)

Wanted: group "Other courses" by provider (e.g. "freeCodeCamp") via drag and drop, rather than encoding the provider into each course's own name (`"freeCodeCamp - React basics"`). Explicitly organisational only — `sideCourses` was already fully isolated from the degree tracker before this, and stayed that way; nothing here reads into any calculation.

**Data model:** new `state.sideCourseFolders: [{id, name}]` array plus `nextSideCourseFolderId` counter. Each course gets `folderId` (`null` = ungrouped, rendered in a root list below all folders; otherwise the owning folder's id). Folders render above the ungrouped root list, in `state.sideCourseFolders` order.

**Why this needed a whole new drag system, not an extension of the existing generic one:** the pre-existing `beginDrag`/`dragState` machinery (still used unchanged for modules, components, and now also for reordering folders themselves via `startFolderDrag`) snapshots ONE fixed sibling list at drag start and only ever computes an insertion index within that fixed group — it has no notion of a *different* container to drop into. Moving a course between folders (or in/out of the ungrouped root) needs exactly that, so it got its own parallel, self-contained implementation: `courseDragState`, `startCourseDrag`, `handleCourseDragMove`, `handleCourseDragEnd`, `hoveredCourseDropFolderId`, `moveSideCourseToFolder`. This keeps every pre-existing draggable list completely untouched — zero shared state or code path with the new system beyond conceptual similarity.

**How cross-container drop detection works:** at drag start, every possible drop container's bounding rect is snapshotted once — the root list's, plus every folder's *whole* card element (header + body together, so a course can be dropped onto a currently-collapsed folder too). Not re-measured on every pointer move, matching the existing system's performance reasoning (nothing else changes size mid-drag, since the dragged row is only translated visually via CSS transform, never removed from flow). On move/release, the pointer's `clientY` is checked against those snapshotted rects to find which container it's currently over (`hoveredCourseDropFolderId`). If it matches the course's origin container, behaviour is an exact same-container reorder, identical in mechanism to the pre-existing pattern (precise insertion index against the original siblings' rects). If it's a *different* container, the course is reassigned to that folder (or back to `null` for the root) and appended to the **end** of that container's list — deliberately not a precise in-list position, since the target container's own rows were never snapshotted at drag start. Fine positioning within a folder after a move is a simple, separate follow-up same-container drag.

**`commitSideCourseOrder(orderedIds, folderId)` signature changed** (previously just `orderedIds` for the whole flat list) — now scoped to reorder only the courses within ONE group (a specific folder, or the root list when `folderId` is null/undefined), leaving every course belonging to a *different* group exactly where it was in the underlying flat array. Rendering re-buckets courses by `folderId` on every render regardless of array interleaving, so only the affected group's relative order actually needs to change for the visible result to be correct.

**Folder CRUD:** `addSideCourseFolder` (a new folder auto-expands, matching the pre-existing `addSideCourseComponent` auto-expand convention), `updateSideCourseFolder` (rename, same contenteditable pattern as course/module names), `deleteSideCourseFolder` — deleting a folder never deletes its courses, they fall back to `folderId: null` (ungrouped), since a folder is a label, not a container things should be destroyed alongside. `toggleSideCourseFolder` mirrors `toggleSideCourseComponents`'s expand/collapse exactly (`expandedFolders`, a runtime-only `Set`, not persisted or undo-tracked, same category as `expandedSideCourses`).

**`patchState` backfill:** `sideCourseFolders` defaults to `[]`, `nextSideCourseFolderId` derived from existing folder ids the same way every other id counter already is, and every course missing a `folderId` field gets `null` — covers both a save from before folders existed at all, and any future inconsistency.

**Testing technique worth reusing — real DOM refs across the Node/jsdom boundary:** end-to-end drag testing needed real event objects carrying real DOM element references (`currentTarget`, etc.), which can't survive being serialized into a `win.eval('...')` string. Fix: call the page's own top-level functions **directly as properties of the jsdom `window` object** (`win.startCourseDrag(fakeEvent, id, folderId)`, `win.handleCourseDragMove(fakeEvent)`, etc. — these already exist as `window` properties automatically, being top-level `function` declarations, no `eval` needed) and construct plain duck-typed fake event objects in Node itself (`{button, clientY, preventDefault(){}, currentTarget: realDomNode}`). The drag functions only ever read `.button`/`.clientY`/`.preventDefault`/`.currentTarget` off the event and never check `instanceof Event`, so a plain object is sufficient. Combined with the pre-existing `getBoundingClientRect` monkeypatching technique (see prior handoff), this fully exercises the real cross-container hit-testing code path (`hoveredCourseDropFolderId` et al.), not just the underlying state-mutation functions in isolation.

Verified: folder create/rename/delete (including that a course survives its folder being deleted); moving a course into and out of a folder via the real pointer-event-driven functions (both directions); reordering within one folder without disturbing a different folder's or the root's order; reordering folders themselves; undo across a folder-create → move → course-create sequence; an export → `patchState`-reimport round trip preserving folder membership; a simulated pre-folders old save loading in cleanly with every course landing in the ungrouped root list; and re-ran every pre-existing calculation regression check (`calcSummary`, `years-container` HTML) to confirm this stayed fully isolated from the degree tracker, as intended.

## Semester comparison charts (prior session, revised four times since first built — this describes the current, final state, not the history)

Two cards added to the existing `charts-container` sidebar (`renderCharts()`'s static shell, alongside grade distribution / completion / marks acquired / assignment spread): a radar/spider chart ("Semester comparison") and a diverging horizontal-bar chart ("Semester target variance"). Both compare Semester 1, Semester 2, and Full Year assignments (the radar chart plots all three as overlapping shapes at once; the benchmark chart shows exactly one of the three at a time via its own filter tabs, see below). Each has five year views (Overall, plus one per year) that respond live to tracker edits.

**Shared data source, `buildSemesterAssignmentData(year)`:** built from individual assignments (module components), not whole modules — a module split across several assessments contributes each assessment's own mark, not one blended number. `year` is `'all'` or a specific year number. Returns `{ sem1, sem2, fullYear }`, each sorted by mark descending, `excl` carried through from the parent module so both charts can fade excluded items the way `renderGradeDistributionChart` already does for modules. Attribution rules:
- A module set to Semester 1 or 2: **every** one of its assignments goes to that semester, regardless of that assignment's own semester tag — the module's own dropdown decides, not a per-assignment vote. This matches how an assignment's own `sem` field is only ever meaningful when the module itself is Full Year elsewhere in the file (`semesterAvg`).
- A Full Year module (`sem === 0`): an assignment individually tagged Semester 1 or 2 goes there; an assignment left untagged (`sem === 0`), or a Full Year module with no breakdown at all, is a genuinely full-year assignment and goes in the third `fullYear` bucket.
- A module with no real assignment breakdown (`gradeByModule` ticked, or no components entered at all) falls back to ONE point using the module's own overall mark, attributed with the same rules above (treating "the whole module" as its one assignment) — so a module without a breakdown doesn't just vanish, it still shows using whatever the coarsest data available for it actually is.
- An assignment with no mark entered is excluded, matching how `buildAssignmentSpreadData` already decides "is this graded" elsewhere in the file.

**Both charts now read the `fullYear` bucket, though the radar chart got it first.** It was originally added only for the radar ("Semester comparison") chart, with the benchmark chart's own `{ sem1, sem2 }` destructure deliberately ignoring it — a later request added it to the benchmark chart too, exposed via its own filter tabs (see below) rather than by changing the shared data function again.

**View selector, `semChartViewTabs(currentView, setterName)`:** a small shared HTML-string helper building a row of pill buttons — Overall plus one per `getYears()`. Each chart owns its own runtime-only view variable (`semRadarView` / `semBenchmarkView`, both default `'all'`, not persisted or undo-tracked — same category as `expandedSideCourses`/`expandedFolders`) and its own setter that redraws only that one chart, not a full `render()`, since switching a view is pure UI state. The two charts' views are fully independent of each other.

**Radar chart (`renderSemesterRadarChart`):** three overlapping polygons — Semester 1 (blue, `--grade-first`), Semester 2 (orange, `--grade-third`), Full Year (gold, `--grade-22` — chosen because green was already spoken for by the 70% threshold ring, and red already carries "danger" connotations from the benchmark chart, so neither felt right for a series that isn't inherently good or bad). Axes are "assignment slots" (1, 2, 3…), not names — a slot can hold up to three different assignments (one from each group, each independently ranked within its own group), so a text label there could only ever honestly show one of up to three. Axis positions are marked with a small neutral-grey dot (not a number — see below) rather than any text. `N` (axis count) is the largest of the three groups' assignment counts for the current view; a group with fewer assignments simply draws a polygon with fewer sides rather than padding out missing slots with fabricated zero-value points. Radial scale is `radialScaleR(mark, rInner, rOuter)`, mapping 40%→`rInner` and 100%→`rOuter` linearly — **but a mark below 40 is not clamped flat at the 40% ring**, it continues the same linear scale inward (floored at a minimum radius of 2 so it never inverts through the centre), since clamping every low score to the same point would defeat the point of spotting outliers. The 70% ring is drawn distinctly (green, dashed, thicker stroke); the other reference rings (40/55/85/100) are plain thin gridlines, values labelled only up the 12-o'clock spoke.

**Axis dot markers, not numbers:** the outer axis-position label used to be a plain slot number (`1`, `2`, …). Replaced with a small dot (`r="2.2"`, neutral `--text-3` grey, distinct from the coloured `r="3"` vertex dots that sit on the polygons themselves) carrying a hover `<title>` that names every assignment actually occupying that slot — `semItemTooltip(sem1[i])` and/or `semItemTooltip(sem2[i])` and/or `semItemTooltip(fullYear[i])`, joined with ` / ` for whichever of the three exist at that index, never fabricating an entry for a group that doesn't reach that slot.

**Bug: hovering only worked on the last-drawn series' dots.** Reported as "hovering only seems to work for Semester 2 points" — root cause was SVG paint order doubling as hit-test order. Each series' filled polygon `<path>` (`polygonFor`) is drawn immediately before that series' own vertex dots, so with three series drawn in sequence (Sem1, then Sem2, then Full Year), Semester 2's semi-transparent fill visually and interactively sits *on top of* Semester 1's dots wherever the two polygons overlap — and an SVG shape with a fill, even at low opacity, is still hit-tested by default, so it silently swallowed hover events meant for whatever was drawn underneath it. Semester 2's own dots worked fine only because nothing was drawn after them to shadow them the same way — this was never actually "Semester 2 works, Semester 1 doesn't", it was "whichever series is drawn last works, every earlier one is at risk wherever a later polygon happens to cover it". Fixed with one attribute: `pointer-events:none` on every polygon's `<path>` (never on the dots themselves), so a fill is purely decorative for hit-testing regardless of what's drawn under or over it — this is the standard SVG fix for exactly this class of "a decorative shape is stealing hover from something underneath it" bug, worth reaching for immediately if any future chart has multiple overlapping filled shapes with independently-interactive elements inside them.

**Diverging benchmark chart (`renderSemesterBenchmarkChart`):** one row per assignment, bar length proportional to `mark - 70`, green (`--green-text`) at or above 70, red (`--danger-text`) below. Shows **exactly one of Semester 1 / Semester 2 / Full Year at a time**, not all of them stacked together, via a second row of pill buttons (`semBenchmarkFilterTabs`, reusing the same `.chart-view-tabs`/`.chart-view-tab` CSS as the year selector, stacked directly beneath it) — `semBenchmarkFilter` (runtime-only, defaults `'sem1'`, same not-persisted/not-undo-tracked category as every other view toggle here), set by `setSemBenchmarkFilter(filter)`. This is independent of `semBenchmarkView` (the year filter): the two combine freely, e.g. "Year 3 + Full Year" shows only Year 3's full-year assignments, confirmed directly. Since only one group is ever visible, the "Semester 1" heading that used to sit above the bars is gone — it would only repeat what the active filter tab already says.

Rows are **not individually labelled with the assignment's name either.** At assignment granularity a single module can contribute several rows instead of one, so a permanent name on every row either forces a very wide chart or crowds the row's own bar and deviation label together — concretely, this is what caused the originally-reported spacing bug: a row with a long module name and a large deviation had nowhere for its own deviation label to sit that didn't overlap the name, since both were anchored within a couple of pixels of each other. Fixed by removing the permanent name column entirely: rows are clustered under a small module-name header (`groupSemItemsByModule`, sorting modules by their own average mark descending, and each module's own assignments by mark descending within its cluster), and each row's own precise identity — module, assignment name, exact mark — is a hover tooltip (`semItemTooltip`) on the bar itself, freeing the width the old name column used toward wider bars instead. The horizontal scale auto-fits to whatever the *currently filtered* group's largest deviation actually is (floored at a minimum span of 5 points) — narrowing to one group at a time also means the scale is no longer stretched to fit two or three groups' worth of range at once, a secondary readability win from the same change.

Full Year assignments only reach this chart because `buildSemesterAssignmentData` already returns a `fullYear` bucket (added for the radar chart, described above) — the benchmark chart previously just ignored it entirely. Adding the third filter option was the only change needed to expose it here; the shared data function itself didn't change for this.

**Shared tooltip helper, `semItemTooltip(item)`:** used by both charts everywhere an assignment's identity needs to be shown — `"ModuleName — AssignmentName: Mark%"`, or just `"ModuleName: Mark%"` for a whole-module fallback point (`isWholeModule`), with `" (excluded from average)"` appended when the parent module is excluded.

**Both charts are pure reads.** Neither ever writes to `state` — confirmed directly by snapshotting `state.modules` before and after repeatedly calling both render functions. They pick up tracker edits automatically because `renderCharts()` runs at the end of the main `render()` pipeline, same as every other chart, including edits to an assignment's own mark specifically (`updateComponent`), not just a module's overall mark.

Verified across the whole arc of this feature: `buildSemesterAssignmentData`'s every attribution rule (module-level vs assignment-level semester resolution, the whole-module fallback, an ungraded assignment excluded, an excluded module's assignments still shown faded, the Full Year bucket populated correctly including the no-breakdown fallback case) using deliberately-constructed test data covering every case at once; ## CSS specificity bug that collapsed the name field to one character per line (two sessions ago — person-reported, reached them despite the previous session's full test pass)

**The bug:** immediately after the Steps/Type feature above shipped, course and part names rendered as a single character per line, running the box down the page instead of across it — a screenshot showed this directly. Root cause: `.side-course-steps, .side-course-type { width: 50px }` never actually applied. Two pre-existing, unrelated base rules already set `width: 100%` on the same elements: `input[type=text] { width: 100%; ... }` (specificity `(0,1,1)` — one attribute selector plus one type selector) and `select { width: 100%; ... }` (specificity `(0,0,1)`). A bare class selector like `.side-course-steps` is only `(0,1,0)` — **lower** than `input[type=text]`'s `(0,1,1)` regardless of which rule is declared later in the file, since specificity always outranks source order and only source order breaks an actual tie. So the inputs stayed at their default 100% width and (critically) kept `flex-shrink: 0` from `flex: 0 0 auto`, meaning each one's oversized flex-basis was completely non-negotiable. With two or three such elements per row each independently demanding ~100% of the container and refusing to shrink, and the name field (`flex: 1 1 auto`, `min-width: 0`) the only element in the row willing to shrink at all, the entire overflow landed on the name field alone — collapsing it toward zero width, at which point normal text wrapping put one character on each line.

**Second, identical-shaped collision found while fixing the first one:** the initial fix — `input[type="text"].side-course-steps` and `select.side-course-type`, both raised to specificity `(0,1,1)` or higher to beat the base rules — worked for Steps immediately, but the Part-level Type dropdown still measured `width: auto` instead of `50px` after the fix. Cause: a pre-existing, more tightly-scoped rule, `.side-course-component-row select { width: auto; min-width: 122px; ... }` (written for the status select that also lives in that row), is *also* exactly `(0,1,1)` — tied with the new `select.side-course-type` rule — and being declared later in the file, won the tie. Resolved by scoping the Type rule to its actual container too: `.side-course-component-row select.side-course-type { width: 50px; min-width: 0; }`, at `(0,2,1)`, which beats `(0,1,1)` outright rather than by accident of file order.

**The fix, both instances:** qualify every new narrow-column selector with its element type (and container, where a same-specificity sibling rule already exists for that container) so it wins the cascade *unconditionally*, not by whichever rule happens to be declared last. This is the same technique the codebase already used, apparently by luck rather than by a documented rule, for `.side-course-component-row select` overriding the base `select` rule for the status dropdown — which is exactly why that one element never had this problem while the newer ones did.

**This is a systemic trap, not a one-off:** `input[type=text] { width: 100% }` and `select { width: 100% }` are both base rules that apply tracker-wide, and both outrank a plain single-class selector. **Any future narrow input or select added anywhere in this file** — not just in Other Courses — needs a selector at least as specific as `input[type="text"].your-class` or `select.your-class` (and scoped to its container too, if that container already has its own same-specificity rule for that element type) to actually get a narrower width than 100%. A plain `.your-class { width: 50px }` will silently lose, exactly as it did twice here, and the failure mode is severe (visually, not just "slightly wrong size") because of the `flex-shrink: 0` compounding effect above. See "Known pre-existing quirks" below for a permanent note to this effect.

**Why the previous session's full jsdom test pass didn't catch this:** jsdom does not implement real layout — `getBoundingClientRect()` always returns all-zero rects (a limitation documented and relied on elsewhere in this file already, see the drag-and-drop testing note under "Testing approach"). None of the previous session's tests measured any element's actual rendered width; they checked *presence*, *order*, *values*, and *persistence*, all of which were completely correct — the elements were exactly where they should be, with exactly the right content, they just had almost no width. **New technique used to verify this properly without a real browser:** jsdom's `getComputedStyle(el).width` *does* correctly resolve CSS cascade and specificity, even though it can't turn a percentage into a pixel value — so `getComputedStyle` reporting `"100%"` on the broken file, and `"50px"` on the fixed one, directly proves which declaration won, which is the exact mechanism that broke. Confirmed both ways: reproduced `"100%"` against the previously-shipped (broken) file first, as positive proof of the diagnosis, then confirmed `"50px"` on the fixed file for the course-level Steps input, the part-level Steps input, and the part-level Type dropdown, plus confirmed the name field's `flex-grow` computed value is still `1` at both levels. This is not a full layout/pixel measurement (that still needs a real browser — no headless browser could be installed in this environment, network access is limited to package registries, not browser-binary hosts), but it is a direct, non-eyeballed check of the actual mechanism that caused the bug, not a proxy for it.

## Course/Part title rows (this session)

Other Courses has no `<table>`, so nothing previously named its own columns anywhere — the person asked for a labelled header row above the Course list inside each folder, and another above the Part list inside each expanded course: `"Course Title" / "Steps" / "Progress"` and `"Part Title" / "Steps" / "Type" / "Progress"` respectively, visually aligned with the real data below.

Deliberately scoped to a **new**, narrower class applied only to the course-row toggle (`renderSideCourseItem`), not the pre-existing `.side-course-toggle-btn` class it shares with the *folder*-header's own toggle ("N courses") — that one keeps its normal auto width, since nothing needs to align with it (there's no header row above the folder list itself, only above the courses inside one). Confirmed directly: the folder-level toggle's computed width is unaffected, and the two toggle buttons render at genuinely different, independently-controlled widths.

**Part rows had no such problem** — `[drag-handle][name][Steps][Type][status select][delete]`, no auto-width element at all, so the part-level header just reuses the already-fixed widths from "CSS specificity bug" / "Type converted to a fixed dropdown" above (50px / 50px / 122px) directly, no new fixed-width work needed there.

**How the header row actually lines up, structurally:** each header is the *same* flex row (same classes, same `gap`) as the data row it labels, with genuine same-class spacer elements standing in for the drag handle, the course-row toggle button, and the delete button — `<span class="drag-handle">`, `<span class="assign-toggle-btn side-course-toggle-btn side-course-row-toggle-btn">`, `<span class="del-btn">` — all `visibility: hidden` (not `display: none`, which would collapse their width to zero and defeat the purpose) so they take up exactly the same space as the real thing without looking like a second, broken drag handle or delete button floating in the header. The visible text labels then sit in dedicated `.side-course-header-name`/`-steps`/`-type`/`-progress` divs, each width-matched to its real counterpart (`flex: 1 1 auto` for the name; `50px` for Steps/Type; `130px` course-level / `122px` part-level for Progress, matching `.side-course-status`'s min-width at each level).

This turns out not to matter: `.side-course-row-main` has never had a `border-top` declared anywhere in the file (only `border-bottom`), so this rule was already removing a border that didn't exist, on either side of this change. Left as-is — noted here so nobody spends time later wondering why it stopped matching; see "Known pre-existing quirks" below for the permanent note.

**Not affected, checked directly rather than assumed:** both drag-and-drop systems (course reordering, and the part reordering inside a course) query siblings by `:scope > .side-course-item` / `.side-course-component-row` — class-based, not positional — so the new header row (which carries neither class) was never at risk of being miscounted as a draggable sibling or shifting anyone else's index math. `commitSideCourseOrder`/`commitSideCourseComponentOrder` both still correctly reorder real rows with the header present. `calcSummary` is unaffected, since none of this is anything but a render-time addition — expanding a folder or a course's parts to reveal a header row never mutates `state`.

Workshop and Lab *do* alias the existing `--accent-text`/`--accent-border` and `--green-text`/`--green-border` pairs directly (they're already exactly "blue" and "green" — no reason to invent near-duplicates), which also means they follow the app's existing accent/green colours automatically if those are ever retuned; the other five (`--type-theory-*`, `--type-review-*`, `--type-quiz-*`, `--type-exam-*`, `--type-cert-*` — Certification Project's *text* colour aliases `--danger-text`, though its border is a fresh colour, since no matching red border pair already existed) are new, defined once in `:root` and re-declared with dark-mode-appropriate values in both `html[data-theme="dark"]` and the `prefers-color-scheme: dark` fallback block, following the exact structure every other themed colour in the file already uses. The aliased ones are *not* redeclared in the dark blocks — CSS custom properties resolve `var()` references against the live cascade at the point of use, not at definition time, so `--type-workshop-text: var(--accent-text);`, defined only once, automatically tracks whichever `--accent-text` is active in the current theme without needing a second copy.

**Verification note specific to this change:** jsdom's `getComputedStyle` does not reliably resolve `var()` references down to an actual colour value (a documented jsdom limitation, distinct from the layout limitation discussed under "CSS specificity bug" above), so colour-coding couldn't be verified the same way the width fix was. Verified instead, directly: (1) the right `type-${slug}` class is actually applied to the select for each of the seven values, and none at all for blank; (2) a CSS rule mapping `.type-${slug}` to `--type-${slug}-text`/`-border` genuinely exists in the stylesheet text, for every slug; (3) both of those custom properties are genuinely defined somewhere in the stylesheet, for every slug. This confirms the *mechanism* is wired correctly end to end — class assignment, matching CSS rule, and a real value behind each variable — even without jsdom being able to report the final resolved hex colour the way a real browser would.

## Testing approach (established across every session, refined again this session)

Every non-trivial or calculation-touching change is verified with a Node.js + jsdom harness: load the actual HTML file, run its script in a simulated DOM (`runScripts: 'dangerously'`), call functions either via `win.eval('...')` (for anything that's just plain data/strings) or directly as `win.functionName(...)` (when a real object reference like a DOM node needs to cross into the jsdom realm — see the folder-drag testing note below; `eval` strings can't carry object references, direct property access on `window` can).

Always includes, at minimum: the specific new behaviour; a regression check that `calcSummary`/`yearAvg` are byte-for-byte unchanged before vs. after the change, run against the same `DEFAULT_DATA`; and, for anything touching table columns, an explicit per-row column-count check against the header (this is the check that would catch a `totalCols`/`extraCols` miscount — see "Feedback box on modules" above for why that mattered). For anything touching `orderLocked`/reordering, an explicit undo check. For any change to `DEFAULT_DATA` itself, additionally diff the whole file against the pre-change version with only the `DEFAULT_DATA` block excluded, to prove nothing else moved. **For any change adding a narrow/fixed-width input or select anywhere in the file, additionally check `getComputedStyle(el).width` (and any other property the new rule sets that a base rule also sets) resolves to the intended value, not just that the element exists with the right class** — see "CSS specificity bug" above for exactly why presence/order/value checks alone missed a bug of this severity, and "Known pre-existing quirks" below for the specific base rules to watch for.

**Before assuming a function's behaviour in a test, read the function.** Every failure this session (see "Bugs found and fixed, this session" above) traced back to guessing how `addSideCourseFolder`/`addSideCourseComponent`/`commitSideCourseOrder` behave instead of checking first — whether something auto-expands, whether a second argument is required, whether a course's containing folder also needs expanding before its DOM exists at all. None of these were app bugs; all four cost real time to diagnose because the assumption looked so plausible that the instinct was to suspect the app first. Fixed by re-reading the actual function source the moment a result looks wrong, before writing more test code around the wrong assumption.

**`getComputedStyle` cannot verify colour**, only layout-adjacent properties like `width`/`flex-grow` that don't depend on resolving a `var()` reference to its underlying value — a separate, jsdom-specific limitation from the layout one below. For anything colour-coded via CSS custom properties (see "Type colour coding" above), verify instead: the right class lands on the right element for the right value, the CSS rule mapping that class to the right custom-property names genuinely exists in the stylesheet text, and those custom properties are genuinely defined somewhere — three structural checks in place of one value check jsdom can't perform.

**If a test calls any function that ends up scheduling a save (`scheduleSave()`'s 1-second debounce — most `updateX`/`addX`/`deleteX` functions do this), wait out that debounce (~1.2s) before calling `dom.window.close()`.** Closing the window with a pending timeout still live crashes the test process when that timeout later fires against a torn-down `document` (see "DEFAULT_DATA rebaked from a real export" above). An easy trap now that more of the test suite calls real mutating functions rather than only reading state.

**Established technique for drag-and-drop (from a prior session):** jsdom's `getBoundingClientRect()` returns all-zero rects, so real layout can't be simulated. Monkeypatch `.getBoundingClientRect` on the relevant elements to return synthetic stacked rects, then call the `startXDrag`/`handleDragMove`/`handleDragEnd` functions directly with plain fake-event objects (`{clientY, button, preventDefault(){}, currentTarget}`) rather than constructing real `PointerEvent`s. This fully covers the insertion-index math and final committed state; only the live pixel-level feel needs a real browser, and that limitation is stated plainly rather than papered over. Extended in an earlier session (see "Side course folders" above) to also cover multiple simultaneous drop-target containers, not just one fixed sibling list.

**A genuine blind spot surfaced in a prior session, worth remembering rather than trying to work around:** jsdom does not simulate real paint order or hit-testing, so a bug where one SVG element visually/interactively sat on top of another and stole its hover events (see "Bugs found and fixed, three sessions ago", item 5) was invisible to the whole test suite despite thorough coverage — every test that checked "does this element have the right `<title>`" passed, because the tooltip content itself was correct, it just could never actually be triggered by a real cursor in a real browser. The fix (`pointer-events:none`) can be verified *structurally* after the fact (confirm the attribute is present, confirm dots don't have it), which is what the test suite does now, but the original bug had to be reasoned out from the code and the person's own description of what they were seeing, not caught by any jsdom test. Any future chart with overlapping filled shapes and independently-interactive children should get `pointer-events:none` on the shapes as a matter of course, not as a reactive fix. **The Steps/Type width bug (see "Bugs found and fixed, the session before this one") is the same underlying limitation (jsdom can't do real layout) showing up in a different property** — `getComputedStyle` can verify *which rule won*, same as structurally verifying `pointer-events:none` is present, but neither one is an actual rendered-pixel or actual-hover-hit-test check. Both are the best available proxy without a real browser, not a substitute for one. No headless browser could be added to fill this gap either (checked this session while verifying the header-row alignment fix): the environment's network access is limited to package registries, not the domains a real browser download needs.

**Several "failures" have turned out to be the test's own bug, not the app** — always re-trace before concluding the app is wrong. Three sessions ago: an early version of the folder-order regression test used a regex that stripped the new `data-year-scroll`/`data-folder-id` attribute but left a stray space behind, producing a false-positive HTML diff; fixed the regex, not the app. Two sessions ago: a debounce-timer-vs-closed-window crash, and a DOM-order assertion that initially mis-identified a `<select>` element by relying on an empty `className` fallback to `tagName`. The session before this one: that same old assertion broke *again*, for a related but new reason — Type becoming a `<select>` itself meant `findIndex(el => el.tagName === 'SELECT')` was no longer unique to the status select; and two other old assertions simply encoded the now-superseded `type: '-'` default, not a bug in either the test or the app, just an old test asserting a design decision that had since legitimately changed. This session: four more, all traced to assuming a function's behaviour rather than reading it first — see the note above.

## Known pre-existing quirks (not necessarily bugs, just worth knowing)
- `DEFAULT_DATA.yearTotalCredits[4]` is `180`, not `120` like the others — never corrected since it hasn't come up, and it's genuinely correct for this institution's Year 4 credit load.
- `DEFAULT_DATA` contains the person's **real, current academic data** (rebaked from a 2026-09-03 export, previously 2026-08-30), not placeholder short-form module codes — used as the fallback whenever storage is empty. If `DEFAULT_DATA` is rebaked again from a future export, re-verify the same things checked when it was last done: `patchState` idempotency on the new default, and that every already-computed field (mark, pct, exam/cw/pres/indiv/group grades, side-course status) the export carries matches what the recompute functions independently derive, not just that the file loads without error.
- Side course folders are single-level only — a folder cannot contain another folder. This is by design, not a current limitation waiting to be lifted; hasn't been asked for.
- A first attempt at the Course/Part Steps+Type feature (Steps at Folder+Course, Type at Course, both defaulting to `''`) was built, then fully reverted at the person's request before the version described above (Steps at Course+Part, Type at Part only) was built from the clean pre-feature file. Confirmed via diff that the revert left zero residue — no leftover CSS, fields, or dead code from the first attempt.
- **`input[type=text] { width: 100% }` and `select { width: 100% }` are tracker-wide base rules that outrank a plain single-class selector in CSS specificity.** This actually broke a shipped feature once already (see "CSS specificity bug" above) — any future narrow input or select added *anywhere* in this file needs a selector at least as specific as `input[type="text"].your-class` or `select.your-class` (and scoped to its container too, if that container already has its own rule for that element type — check for one before assuming a single fix is enough, a second collision at the container level is exactly what happened the first time this was fixed). This is now the single most important layout gotcha in the file to remember before adding any new compact field.
- **`.side-course-folder-body .side-course-item:first-child .side-course-row-main { border-top: none; }` is dead code.** `.side-course-row-main` has never had a `border-top` declared anywhere (only `border-bottom`), so this rule has always removed a border that didn't exist. Confirmed while checking that the new Course-level title row (which is now genuinely the first child of `.side-course-folder-body`, ahead of the first real course item) didn't silently break something real — it didn't, because there was nothing real to break. Left in place rather than removed, since removing dead CSS wasn't asked for and isn't worth an unscoped edit; noted here so it doesn't look like a new bug next time someone notices the selector no longer matches its "first" target.

Reasoning given directly to the person when this shipped (same three columns, would otherwise be the one unlabelled list) but not yet re-confirmed as correct by them specifically — if it turns out to be unwanted, removing it is a one-line change (drop `sideCourseColumnHeaderRow() +` from the root-list template in `renderSideCourses`, leave the folder-body one alone).
